# 백엔드 요청 — 트랙 duration 오판(VBR Xing 헤더 누락) 파일 교체 및 파이프라인 개선

작성일: 2026-09-20
요청 출처: 모바일 앱 v3.192 (PLAN.md) — "냥냥냥 재생시간이 실제보다 짧게 보이고 진행바가 중간에 끊김, 가사 싱크도 그 지점에서 정지" 사용자 리포트

## 배경

track id `6aa3ec295f11b57ba518f5e8`(냥냥냥)의 MP3 파일이 **VBR인데 Xing/Info/VBRI 헤더가 없습니다**. 실측(공개 `stream-proxy`로 수신 후 프레임 분석):

- 실제 오디오 길이: **157.86초(2:38)** — 48kHz, 프레임 비트레이트 128~320kbps 혼재(VBR)
- 첫 프레임이 320kbps → CBR 가정 추정 시 3,650,496B×8÷320kbps = **91.26초** = 현재 DB `duration_sec: 91`과 정확히 일치

즉 ① 백엔드의 duration 계산(91초)과 ② 모바일 재생 엔진(Android ExoPlayer ConstantBitrateSeeker / iOS AVFoundation)의 길이 추정이 **같은 원리로 같이 오판**하고 있습니다. 결과: 진행바 조기 종료 표시, 가사 싱크 정지처럼 보임, seek 좌표 왜곡(바이트-선형 매핑). 대조군 2곡(Xing 헤더 있음)은 실측과 API `duration_sec`이 일치 — 이 파일만의 문제입니다.

모바일 v3.192에서 표시 보정(엔진값·재생위치·`duration_sec` 중 최대값 사용)은 넣었지만, **seek 정확도와 엔진 자체의 길이 인식은 파일을 고치기 전까지 해결 불가**합니다. 70% 재생기록(별 적립)도 세 값이 전부 91초라 63.7초에 조기 발화하는 상태로, 서버의 duration 갱신 전에는 해소되지 않습니다.

## 요청 사항

### 1) 개별 데이터 수정 — 냥냥냥 파일 재먹싱 + duration 갱신

```bash
ffmpeg -i in.mp3 -c:a copy out.mp3   # 재인코딩 없음 — Xing 헤더만 재작성
```

- 재먹싱한 파일을 **동일 object key로 교체** 저장 (URL 불변 → 앱/캐시 영향 없음)
- DB `duration_sec`: **91 → 158** (실측 157.86초) 갱신

### 2) 파이프라인 개선 — duration을 디코드 실측으로 저장

업로드/생성 파이프라인에서 duration을 헤더(첫 프레임 비트레이트) 추정이 아닌 **디코드 실측**으로 산출해 주세요.

```bash
ffprobe -v error -show_entries format=duration -of default=noprint_wrappers=1:nokey=1 in.mp3
```

- 권장: 저장 시 항상 `ffmpeg -c:a copy` 재먹싱을 한 번 거치면 Xing 헤더가 재작성되어 클라이언트 재생 엔진의 오판까지 원천 차단됩니다.

### 3) 기존 트랙 전수 점검

전체 트랙에 대해 "헤더 추정 duration vs 디코드 실측" 괴리가 **5초 이상**인 목록을 뽑아 주세요.

- 간이 스크리닝: `파일크기(byte)×8 ÷ duration_sec` 로 역산한 비트레이트가 실측 평균 비트레이트와 크게 어긋나는 트랙 우선
- 괴리 트랙은 1)과 동일하게 재먹싱 교체 + `duration_sec` 갱신

## 모바일 측 후속 작업

- 파일 교체 후 별도 배포 불요 — v3.192 방어 보정은 일반 방어로 유지
- 교체 확인되면 냥냥냥에서 `[PlayerScreen] duration mismatch` DEV 경고가 더 이상 찍히지 않는지로 검증 가능

## 우선순위

중간. 재생 핵심 UX(진행바·가사 싱크·seek)에 직접 영향이며, 1)은 파일 1개 교체라 저비용. 2)·3)은 여유 시 처리해 주세요.
